# ТЗ: источник данных для учебного лейкхауса

## Контекст

Есть работающий стенд в `docker-compose.yml` в корне репозитория: MinIO (S3), Lakekeeper (Iceberg REST catalog), Postgres под метаданные каталога, Trino. Стенд поднимается одной командой `docker compose up -d` без ручных действий.

Нужен источник данных, из которого будут делаться три типа загрузок в лейкхаус: батч по инкременту, выгрузка файлов, и CDC через логическую репликацию. Источник один на все три сценария.

## Что требуется сделать

Добавить в существующий `docker-compose.yml` два сервиса и сопутствующие файлы:

1. `source-db` — Postgres с прикладной схемой, настроенный под логическую репликацию.
2. `source-generator` — контейнер с Python-скриптом, который наполняет базу и непрерывно порождает изменения.

## Жесткие ограничения

- Существующие сервисы (`minio-tblrka`, `minio-init`, `lakekeeper-db`, `lakekeeper`, `migrate`, `lakekeeper-init`, `trino`) не изменять. Только добавить новое.
- Имена сервисов строчными буквами через дефис.
- У всех образов явные теги, никаких `latest`.
- Тома именованные, монтируются туда, куда программа реально пишет.
- Порты наружу публиковать на нестандартных номерах, чтобы не конфликтовать с локальными сервисами (в проекте уже занято 9222, 9223, 15432, 18181, 18080).
- Все init-шаги идемпотентны: повторный `up -d` и полный цикл `down -v && up -d` проходят без ошибок.
- Никаких ручных действий после запуска: схема, права, публикация и начальные данные создаются сами.
- Файлы конфигурации и SQL класть в папку `source/` рядом с корнем проекта.

## Схема данных

Схема `shop` в базе `source`.

### customers (справочник)

- `customer_id` bigint, первичный ключ
- `full_name` text
- `city` text
- `segment` text, одно из: retail, b2b, vip
- `created_at` timestamptz
- `updated_at` timestamptz

### delivery_points (справочник)

- `point_id` bigint, первичный ключ
- `name` text
- `city` text
- `address` text
- `lat` numeric(9,6)
- `lon` numeric(9,6)
- `point_type` text, одно из: pickup, locker, courier_zone
- `created_at` timestamptz
- `updated_at` timestamptz

### orders (факт)

- `order_id` bigint, первичный ключ
- `customer_id` bigint, внешний ключ на customers
- `point_id` bigint, внешний ключ на delivery_points
- `status` text, одно из: created, assembling, in_delivery, delivered, cancelled
- `total_amount` numeric(12,2)
- `items_count` int
- `is_cancelled` boolean, по умолчанию false
- `created_at` timestamptz
- `updated_at` timestamptz
- `planned_delivery_at` timestamptz
- `actual_delivery_at` timestamptz, null пока заказ не доставлен

Индексы: по `updated_at` на всех трех таблицах (по ним будет идти инкрементальная выгрузка).

## Настройка под CDC

Это то, что в реальном проекте делает владелец базы. Нужно сделать заранее, при подъеме стенда:

- `wal_level = logical`, `max_replication_slots` и `max_wal_senders` не меньше 4
- отдельная роль `cdc_user` с паролем, с атрибутами LOGIN и REPLICATION, с правом SELECT на схему `shop`
- публикация `shop_pub` на три таблицы схемы `shop`
- `REPLICA IDENTITY FULL` на всех трех таблицах, чтобы в событиях апдейта и удаления приезжали прежние значения
- отдельная прикладная роль для генератора, не совпадающая с cdc_user

Слот репликации не создавать, его создаст коннектор.

## Поведение генератора

Два режима, управляются переменной окружения.

**seed** — начальное наполнение: клиенты, точки доставки, заказы за прошедший период (даты создания разнесены по времени назад, а не все одним моментом). Выполняется один раз, повторный запуск на непустой базе ничего не ломает.

**run** — непрерывная работа циклом с настраиваемой паузой. В каждом цикле:

- создаются новые заказы
- существующие заказы двигаются по статусам: created → assembling → in_delivery → delivered. Переход происходит не мгновенно, а спустя время, разное для разных заказов
- при переходе в delivered проставляется `actual_delivery_at`
- часть заказов отменяется: `status = cancelled`, `is_cancelled = true` (логическое удаление)
- редко обновляются справочники: клиент меняет город или сегмент, точка меняет тип или адрес
- редко и фоново выполняется физическое удаление: `DELETE` заказов старше заданного срока и удаление отдельных клиентов вместе с их заказами (имитация запроса на удаление персональных данных)

Каждое изменение строки обновляет `updated_at`.

**Специально заложенная аномалия.** У небольшой доли операций (доля настраивается, по умолчанию около 2 процентов) `updated_at` проставляется задним числом, на несколько минут или часов раньше реального момента изменения. Это нужно, чтобы на стенде воспроизводилась классическая проблема инкрементальной выгрузки по дате обновления: такие строки пропускаются при загрузке по верхней границе. Аномалию не чинить, она часть задания.

## Параметры

Все через переменные окружения с разумными значениями по умолчанию: режим, пауза между циклами, количество сущностей при seed, интенсивность новых заказов, доли отмен, физических удалений и аномальных `updated_at`, параметры подключения к базе.

## Критерии приемки

1. `docker compose down -v && docker compose up -d` поднимает весь стенд, включая новые сервисы, без ручных действий и без ошибок.
2. После подъема в базе есть данные: заказы, клиенты, точки доставки.
3. `SELECT count(*) FROM shop.orders` растет со временем, статусы заказов меняются.
4. `SHOW wal_level` возвращает logical; публикация `shop_pub` существует и включает три таблицы; `cdc_user` может подключиться и имеет атрибут репликации.
5. Повторный `docker compose up -d` на живом стенде не приводит к ошибкам и не дублирует начальные данные.
6. В логах генератора видно, что он делает: сколько вставил, обновил, удалил за цикл.
7. В коде генератора есть комментарий, помечающий место, где реализована аномалия с `updated_at`.

## Чего делать НЕ надо

- Не поднимать Kafka, Kafka Connect, Debezium и любые компоненты загрузки. Источник и только источник.
- Не создавать таблицы в Iceberg и не трогать Trino, Lakekeeper и MinIO.
- Не писать код загрузки данных в лейкхаус.
