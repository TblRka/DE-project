# ТЗ: ограничение роста базы источника (дополнение)

Относится к проекту `shop-source`. Остальное поведение не менять.

## Требование

База источника не должна занимать больше 3 ГБ. Это жесткая граница: генератор сам подстраивает свое поведение так, чтобы в нее укладываться, без ручного вмешательства.

Учитывать надо не только данные: в размер входит и WAL, который при логической репликации растет быстрее обычного. Ориентироваться на суммарный размер того, что лежит в томе базы.

## Что сделать

1. Добавить переменные окружения: жесткий лимит размера (по умолчанию 3 ГБ) и порог срабатывания в процентах от него (по умолчанию 80).
2. Генератор периодически (раз в N циклов, N настраиваемый) измеряет фактический размер: `pg_database_size` плюс суммарный размер файлов WAL (`pg_ls_waldir`). Значение пишет в лог.
3. Пока размер ниже порога, генератор работает как сейчас: создает новые заказы заданным темпом, двигает статусы, правит справочники, удаляет.
4. При достижении порога генератор переходит в режим удержания: новые заказы не создаются, а вместо них удаляются самые старые доставленные или отмененные заказы, примерно столько же, сколько создавалось бы. Переходы статусов, правки справочников и остальные удаления продолжаются, поток изменений не прекращается.
5. Если размер продолжает расти и подходит к жесткому лимиту, удалять агрессивнее, пока не опустится ниже порога.
6. Когда размер снова ниже порога, вернуться к обычному режиму.
7. Каждое переключение режима писать в лог отдельной строкой, чтобы было видно, что произошло и почему.

## Что учесть при реализации

- Обычный `DELETE` не возвращает место операционной системе, он лишь освобождает его для повторного использования внутри таблицы. Поэтому размер файлов стабилизируется, но не уменьшится, и это ожидаемое поведение. `VACUUM FULL` в генераторе не вызывать, он блокирует таблицу целиком.
- Не пересчитывать число строк полным `count(*)` на каждом цикле: держать счетчик в памяти, корректировать на вставленные и удаленные, полный пересчет делать редко.
- Измерение размера тоже не бесплатное, поэтому раз в N циклов, а не каждый.
- Темп создания новых заказов по умолчанию снизить примерно до 20 в минуту, параметр оставить настраиваемым.

## Про WAL

Отдельным разделом в README предупредить: незанятый слот логической репликации не дает чистить WAL, и он растет неограниченно, обходя любые лимиты генератора. Привести команды для просмотра слотов (`pg_replication_slots`) и удаления неиспользуемого (`pg_drop_replication_slot`). Сам слот не создавать.

Если это возможно без риска для CDC, задать в конфигурации Postgres разумные ограничения на размер WAL, чтобы он не разрастался при обычной работе.

## Критерии приемки

1. При выставленном низком лимите (например 200 МБ через переменную окружения) генератор переходит в режим удержания, и размер базы перестает расти. В логе видно переключение режима и текущий размер.
2. В режиме удержания поток изменений не прекращается: в логе видны переходы статусов, правки справочников и удаления.
3. После снижения размера ниже порога генератор возвращается к созданию новых заказов, это видно в логе.
4. Размер базы при длительной работе с настройками по умолчанию не превышает 3 ГБ.
5. `docker compose down -v && docker compose up -d` по-прежнему проходит дважды без ошибок.

## Чего делать не надо

- Не менять схему данных, роли, публикацию и настройки репликации.
- Не трогать аномалию с `updated_at`.
- Не вызывать `VACUUM FULL` из генератора.
- Не трогать проект `DE-project`, работать только в `shop-source`.
